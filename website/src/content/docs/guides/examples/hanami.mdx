[Hanakai](https://hanakai.org/) brings together Hanami, Dry, and Rom. This example uses all three for the same customer-registration and invoice-issuance workflow as [Rails](/guides/examples/rails/). Customers and Billing are Hanami slices, each running inside its own Carton. The Shop Carton exports its Hanami Rack application to Main. [Source on GitHub](https://github.com/dtcristo/carton/tree/main/examples/hanami).

The application follows Hanami's shape: `config/app.rb`, `config/routes.rb`, `config/providers/`, `config/db/migrate/`, and `slices/`. Actions handle HTTP, operations implement workflows, contracts validate input, repos query relations, and views render templates. The app consists of slices, so it needs no root `app/` components. Carton adds Entrypoints beside those directories and explicit boot bridges; it changes no framework or runtime implementation.

| Toolkit | What it does here |
| --- | --- |
| Hanami | Application and slice lifecycle, routing, actions, JSON body parsing, dependency containers and providers, views, CLI, and database migrations |
| Dry | Contracts, strict input types, dependency injection through `Deps`, and operations returning `Success` or `Failure` |
| Rom | SQLite gateways, inferred relations, commands, repositories, and immutable query results |

## Workflow

1. `POST /customers` with `customer: { name: "  Ada  " }` registers Ada and returns her ID and trimmed name.
2. `POST /invoices.json` with `invoice: { customer_id: 1, subtotal_cents: 4200 }` issues an invoice for an existing customer. Billing's provider imports Customers and injects its Directory into the operation.
3. `GET /invoices/1.json` returns `id`, `customer_id`, `subtotal_cents`, `tax_cents`, and `total_cents`. `GET /invoices/1` renders HTML with the escaped customer name and formatted total.

Both POSTs return 201. Form fields and JSON bodies work. Ten percent tax rounds half up using integer cents: 4200 yields 420 tax and 4620 total; 5 yields 1 tax. Reading a stored invoice retains its original tax. Blank names, fractional amounts, booleans, and invalid IDs return 422 with contract errors; missing customers or invoices return 404. A missing or non-object POST envelope, or malformed JSON, returns 400.

## Application and slices

The Framework Carton loads Hanami once. Shop imports Framework and defines the conventional `Shop::App` in `config/app.rb`. Hanami discovers `config/slices/billing.rb` and `config/slices/customers.rb`; those files import the Cartons instead of requiring Second Copies. Each exports its module containing a configured `Slice` subclass. Hanami then registers and prepares those existing slice classes through its ordinary slice lifecycle.

`Framework.register` binds the exported namespaces for Hanami's qualified constant lookups. It accepts a repeated binding to the same module and rejects a conflicting one. The dependencies remain shared Ruby objects. `Carton.setup_bundle` activates the same lockfile in each Carton; it does not make separate dependency versions for this example.

## Loading boundaries

Each slice's Entrypoint sets up its own Zeitwerk loader and tells Hanami's loader to ignore that source tree. Hanami still discovers the slice's components and supplies its `Deps` mixin; resolving a component triggers the Carton-owned autoload. Action bodies, operations, contracts, and repo methods consequently execute in their domain's Carton Box in both lazy and eager modes. Slice configuration, providers, migrations, and inherited framework behavior execute beside Hanami in Framework.

The explicit `Ruby::Box.current.require_relative` in Framework's lifecycle bridge anchors deferred framework requires there, even while Shop is being imported. The CLI uses the same public Ruby API. Without that anchor, a deferred require during a nested Import can load part of Dry into the importing Carton. Neither bridge exposes a Box to Importers or uses private Carton state. Main and Master receive no Hanami, Dry, or Rom constants.

## Operations, contracts, and persistence

Customers validates and trims a name before inserting through its repo. Its Directory returns a result containing a plain customer Hash. Billing obtains that Directory through a conventional provider and `Deps`, validates invoice attributes, verifies the customer exists, calculates tax, and persists through its own repo. A failed step returns before the insert. There is one write per operation.

The custom Dry type accepts integer form strings while preserving strict integer checks for JSON. Dry's default params integer type also coerces floats, which would silently truncate a fractional subtotal. The contracts therefore use `Types::IntegerParam` for both the customer ID and subtotal.

Hanami's database provider manages the shared SQLite gateway; each slice owns its ROM relations and repos. The app's migrations create both tables and the customer foreign key. Importing Shop prepares the application and creates no tables. Run migrations before serving requests or requesting eager boot. Database state survives process restarts.

## HTTP and views

Hanami's error renderer maps malformed JSON from its body-parser middleware to 400 in every environment. Actions translate operation results into status codes and JSON. The show action rehydrates the invoice with its stored tax and either returns JSON or renders its Hanami view. Template escaping handles customer names; the view formats integer cents without floating point arithmetic.

## Run

From the repository root:

```sh
bundle exec rake example:hanami
```

The task installs the locked bundle, runs the temporary-database demo, tests requests and Box ownership in lazy and eager modes, checks CLI commands and persistence across fresh processes, and starts Puma in production mode for a real HTTP workflow. For a persistent local app:

```sh
cd examples/hanami
bundle install
RUBY_BOX=1 bin/hanami db migrate
RUBY_BOX=1 bin/hanami routes
RUBY_BOX=1 bin/hanami run 'puts Hanami.app.slices.keys.inspect'
RUBY_BOX=1 bin/hanami server --host=127.0.0.1 --port=2300
```

In another terminal:

```sh
curl -H 'Content-Type: application/json' -d '{"customer":{"name":"Ada"}}' http://127.0.0.1:2300/customers
curl -H 'Content-Type: application/json' -d '{"invoice":{"customer_id":1,"subtotal_cents":4200}}' http://127.0.0.1:2300/invoices.json
curl http://127.0.0.1:2300/invoices/1.json
curl http://127.0.0.1:2300/invoices/1
```

The default database is `db/shop.sqlite3`; Hanami derives `db/shop_test.sqlite3` in test. `DATABASE_URL` selects another SQLite URL, with the same test-name derivation. A development migration also migrates the test database through this app's CLI bridge. Set this example's `HANAMI_EAGER_LOAD=true` to boot all providers and components up front, after migrating. Otherwise components resolve lazily.

## Limits

Use this app's `bin/hanami`, which imports Shop before invoking the standard CLI in Framework. Verified commands are `db migrate`, `routes`, `run`, and `server`. Stock `bundle exec hanami`, generators, console, asset builds, mailers, and background jobs are not covered. They are unnecessary for this workflow. Restart after source edits; no Carton reloading hooks are installed. Shared framework classes and registries remain mutable shared objects, as in the Rails example.

For the underlying conventions, see Hanami's [slices](https://hanakai.org/learn/hanami/v3.0/app/slices), [operations](https://hanakai.org/learn/hanami/v3.0/operations), and [database configuration](https://hanakai.org/learn/hanami/v3.0/database/configuration) guides.
