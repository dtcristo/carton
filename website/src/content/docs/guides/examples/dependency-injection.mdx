A domain Carton cannot see the application's database models, payment client, or logger by constant name. Pass the objects it needs through ordinary constructor arguments. This checkout Carton calculates an order's total, charges it, saves the payment reference, and logs success. Its host supplies storage, payments, and logging. [Source on GitHub](https://github.com/dtcristo/carton/tree/main/examples/dependency_injection).

```
main.rb                  # Main: sets up the bundle, imports checkout, wires adapters
adapters.rb              # Main: JSON order storage and simulated payments
checkout.rb              # Carton Entrypoint: export Checkout
checkout/service.rb      # Inside the Carton: Checkout::Service
test/checkout_test.rb    # Imports checkout and supplies fakes
test/host_test.rb        # Imports checkout and exercises the file-backed adapters
```

## The Carton

The Carton never requires the host or sets up a bundle. Its Public Surface is a constructor and one method:

<ExampleFile path="dependency_injection/checkout.rb" />

<ExampleFile path="dependency_injection/checkout/service.rb" />

The injected objects need only these methods:

| Object | Method | Result |
| --- | --- | --- |
| `orders` | `fetch(id)` | An order Hash with `:id` and `:items`; each item has integer `:unit_price_cents` and `:quantity` |
| `orders` | `save(order)` | Stores the order with its `:payment_id`; return value is ignored |
| `payments` | `charge(order_id:, amount_cents:)` | A payment ID String, or raises on failure |
| `logger` | `info(message)` | Logs the message; return value is ignored |

## The host

`main.rb` loads the adapters with `require_relative`, then imports `checkout` and wires them in:

<ExampleFile path="dependency_injection/main.rb" />

These are shared Ruby objects, not copies or remote proxies. Their methods run in the Box where they were defined, so the host's adapters still resolve `JSON` and `Logger` in Main. The Carton calls the objects it receives without seeing the host's constants. Orders and results are plain Hashes, Arrays, Strings, and Integers, so neither side needs the other's types. The service saves a new Hash instead of mutating the order it fetched.

The demo host stores orders in JSON and records simulated charges in a temporary directory. No real payments, network, or credentials are involved. A real app would supply its database repository and payment client through the same methods. The example omits payment retries, idempotency, and recovery if saving fails after charging.

If a dependency raises, the exception reaches the Importer unchanged. A declined payment does not save the order or log success.

## Tests

Both tests import the real checkout Carton. `checkout_test.rb` supplies fakes and checks totals, adapter calls, and failures without files or a payment provider. It defines the payment error in Main and rescues it there after it passes through the Carton. `host_test.rb` supplies the demo adapters and checks the stored order, charge, and log output. Neither loads the Carton's Interior directly.

Every Shared Import returns the same Export module, but each `Checkout::Service.new` receives its own dependencies, so there is no module-level state to reset between tests.

## Run

```sh
bundle exec rake example:dependency_injection
```

Once the bundle is installed, run the host or tests directly:

```sh
RUBY_BOX=1 ruby examples/dependency_injection/main.rb
RUBY_BOX=1 ruby examples/dependency_injection/test/checkout_test.rb
RUBY_BOX=1 ruby examples/dependency_injection/test/host_test.rb
```
