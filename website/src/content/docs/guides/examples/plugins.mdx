Two plugins that need incompatible versions of the same gem cannot load into one Ruby process. This month-end report runner loads both anyway, each in its own Carton. [Source on GitHub](https://github.com/dtcristo/carton/tree/main/examples/plugins).

## The problem

Each plugin sends the month's orders to a service with Faraday, and each is stuck on a different major version:

| Plugin | Gemfile | Why it can't move |
| --- | --- | --- |
| `crm` | `faraday ~> 1.10`, through its vendored `crm_client` | calls `request :basic_auth`, which 2.0 removed |
| `webhook` | `faraday ~> 2.0` | calls `request :authorization, :basic, ...`, which 2.0 added |

Plain Ruby activates one version of a gem per process. Load `crm` first and `webhook` fails:

```
Gem::LoadError: can't activate faraday-2.15.0, already activated faraday-1.10.6
```

No single lockfile satisfies both, so Bundler can't help. The usual fixes are to fork one plugin, run each in its own process, or wait for its maintainer to upgrade. `crm` also carries a legacy patch that prints every `Float` with two decimals, which in plain Ruby changes `Float#to_s` for the host and `webhook` too.

## The host

`main.rb` finds each directory in `plugins/`, imports it as a Carton, and calls the plugin interface, `title` and `call(orders)`:

<ExampleFile path="plugins/main.rb" />

```
main.rb                        # the host: finds, imports, and runs plugins
plugins/
  crm/
    lib/crm.rb                 # Entrypoint: imports crm_client, export Crm
    lib/crm/
      float_as_money.rb        # the Float#to_s patch, inside the Carton
    cartons/crm_client/
      Gemfile, Gemfile.lock    # faraday 1.10.6
      lib/crm_client.rb        # Entrypoint: setup_bundle, export CrmClient
  webhook/
    Gemfile, Gemfile.lock      # faraday 2.15.0
    lib/webhook.rb             # Entrypoint: setup_bundle, export Webhook
```

The host never loads Faraday and has no Gemfile. Adding a plugin is a new directory with its own `Gemfile`, or with Cartons that have one. Both plugins use Faraday's test adapter, so the example runs offline.

## Sharing a Carton between plugins

A Carton loads once per process, keyed by its Entrypoint's path. If both plugins import the same third Carton, such as a shared path gem, they get one copy, built with the gem versions its First Importer selected. When the other plugin's Carton Bundle locks a different version of a gem that Carton uses, its import raises `Carton::ImportError` naming the gem and both versions, rather than sharing a copy built against the wrong one. Either lock the same versions in both plugins, or give each its own copy: a Carton at another path, such as `crm`'s vendored `crm_client`, is a separate Carton.

## Testing plugins

Test a plugin the way the host uses it: import its directory and call its interface. `test/webhook_test.rb` does this with minitest from `test/Gemfile`, separate from the plugin's Carton Bundle, so the host still needs no Gemfile:

```sh
RUBY_BOX=1 ruby examples/plugins/test/webhook_test.rb
```

Each Carton loads once per process, so a plugin's state carries from one test to the next. Keep plugins stateless, or run each plugin's tests in its own process. To test a plugin's Interior, require its files directly without Boxes; see [Testing](/guides/testing/).

## Limits

- Box is not a security boundary. Plugins run with the host's full privileges, so load only plugins you trust.
- Objects are shared, not copied. A plugin can mutate what the host passes it, so the host freezes `ORDERS`. Pass plain values such as Strings, Numbers, and Hashes: each Box loads its own gem classes, so a `Faraday::Response` from one plugin is not a `Faraday::Response` to the host or the other plugin.
- Box isolates patches to builtins such as `Float`. Classes a plugin defines are shared, so reopening another plugin's class changes it everywhere; see [Sharing classes and services](/guides/sharing-classes/).
- `ENV` is process-wide. `setup_bundle` restores it, but load plugins while booting, before starting threads that read `ENV`.
- Each Box costs tens of milliseconds to create, plus its own gem loading.
